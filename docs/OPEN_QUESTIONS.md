# Open Questions

Every ambiguity below was resolved by guessing while writing `SCREEN_INVENTORY.md`, `DATA_MODEL.md`, and `API.md`. Answer these before Claude Code starts M1 — a wrong guess here costs more the further downstream it's caught.

1. **Program vs. Course nesting.** The spec models `Program → Course → Module → Lesson`, but no screen ever shows a program containing more than one course — "Forge Full Stack Developer" is treated as a *course* on `my_learning_lumoraspace` and as a *program* on `program_detail_forge_data_analyst_desktop`. Assumed: keep the 4-level nesting for future flexibility, but every seeded `Program` gets exactly one same-named `Course`. If programs will never bundle multiple courses, `Course` should probably be collapsed out entirely.

2. **Self-paced vs. cohort-only enrollment.** Every enrollment screen (`enrollments_lumoraspace_admin`, `batch_detail_*`) shows a batch. Nothing in the export shows a learner enrolled without a batch. Assumed (per the prompt pack's own warning): `Enrollment.batchId` is nullable so self-paced enrollment is possible later. Confirm whether MVP needs self-paced at all, or whether `batchId` should be required.

3. **What marks a lesson "complete."** `lesson_experience_middleware_security` shows both a video progress bar *and* an explicit "Mark as Complete" button. Assumed: completion is the explicit action (`LessonProgress.completed`), and `videoProgressPercent` is stored only as a resume-position hint, not a completion trigger. If auto-complete-on-100%-watched is actually wanted, the rollup logic changes.

4. **Quiz vs. Assessment are unified.** `practice_hub_lumoraspace` lists "Quizzes," "Assignments," and "Assessments" as three parallel activity types, and `quiz_interface_*` and the admin `assessment_builder_*`/`edit_assessment_mobile` screens share an identical timer/question/navigator UI. Assumed: Quiz and Assessment are the same underlying `Assessment` model, distinguished only by field values (e.g. a "quiz" has no `passingScorePercent` or doesn't gate certification). If quizzes need their own lighter-weight table, this needs revisiting.

5. **"Reviews" means mentor grading, not course ratings.** `reviews_lumoraspace`/`reviews_mobile` (mentor nav item "Reviews") could plausibly mean either mentor-graded submissions or learner-authored course ratings. Assumed the former, based on `reviewing_alex_morgan` and `review_submission_mobile` both showing a rubric-based submission review, not a star rating.

6. **`SessionAttendee` per-attendee percentage.** `session_detail_sql_q_a`'s attendance list shows a % next to each learner (e.g. "72%", "85%") alongside present/absent controls. Assumed this is a quiz/engagement score tied to that session, modeled as `engagementPercent` — its actual source (a live poll? a follow-up quiz?) is unclear.

7. **Batch-level vs. program-level mentor assignment.** `batch_detail_forge_data_analyst_batch_04` shows mentors assigned per batch; `program_detail_forge_data_analyst_desktop` shows an "Assigned Mentors" count at the program level. Assumed the program-level count is just the distinct union of mentors across that program's batches (`MentorAssignment` stays batch-scoped) rather than a separate program-level assignment.

8. **`batch_detail_mobile` role.** Unlike its desktop counterpart (clearly ADMIN, full sidebar), the mobile batch-detail screen has no chrome indicating admin vs. mentor. Assumed ADMIN for consistency with `batch_detail_forge_data_analyst_batch_04`, but a mentor plausibly needs the same view (read-only) for their own batches.

9. **`settings_mobile_1` role.** This is a generic settings menu (Profile/Account/Notifications/Learning Preferences/Security) with nothing indicating which role it belongs to. Assumed it's the shared account-settings menu any signed-in user sees, reusing the learner settings endpoints regardless of role.

10. **Certificate detail vs. public verification.** `certificate_detail_lum_2026_00124` is an ADMIN screen (has Revoke/Download actions, full sidebar). No screen in the export represents the public, logged-out `/verify/[certificateId]` page the prompt pack explicitly requires. Assumed that page is a stripped-down (no admin actions) render of the same certificate data, and API.md's `GET /verify/:certificateNumber` was invented rather than sourced from a screen.

11. **Marketing chrome wrapping authenticated pages.** Several desktop learner screens (`assignment_details_sql_optimization`, `course_overview_full_stack_developer`, `my_learning_lumoraspace`, `student_progress_lumoraspace`, `program_details_full_stack_developer`) are wrapped in the logged-out marketing header/footer (Programs / Why LumoraSpace / Login nav, Discord/Telegram footer) even though the page content is authenticated learner data. Assumed this is a Stitch-export inconsistency (these came from a different design pass than the sidebar-nav learner screens like `student_dashboard_home`), not an intentional design where the marketing shell wraps logged-in pages. The sidebar-nav variant (`student_dashboard_home`-style) is treated as canonical for the real app shell.

12. **Duplicate progress-dashboard designs.** `student_progress` (sidebar-nav shell) and `student_progress_lumoraspace` (marketing shell, see #11) show the same feature — a learner progress dashboard — with different layouts and partially different stats (one has a "skills matrix" with %, the other a plain skills-acquired list). Assumed both map to the same `/learn/progress` route and are alternate visual explorations to reconcile during the Antigravity visual-parity pass, not two different features.

13. **Admin settings navigation is inconsistent across three screens.** `settings_general_lumoraspace_admin` lists a 7-item settings nav (General/Roles & Permissions/Notifications/Integrations/Payments/Certificates/Security); `settings_integrations_lumoraspace_admin` lists a different 7 items (General/Account/Security & Privacy/Notifications/Branding/Integrations/Roles & Permissions); `settings_roles_permissions_lumoraspace_admin` lists yet another 6 (General/Security & Auth/Roles & Permissions/Notification Rules/API Webhooks/Billing & Usage). Assumed these need to be reconciled into one settings IA before M5 — API.md picks `/admin/settings/{general,integrations,roles}` as a reasonable minimum, not an exhaustive match to any one screen.

14. **"External Auditor" is a 4th role.** `settings_roles_permissions_lumoraspace_admin` lists a read-only "External Auditor" role alongside Administrator/Mentor/Learner. The prompt pack scopes MVP to exactly 3 roles. Assumed External Auditor (and the general custom-roles UI on that screen) is Phase 2, and MVP's `Role` enum stays `LEARNER | MENTOR | ADMIN`.

15. **No self-serve Mentor/Admin signup.** `sign_up_lumoraspace` has no role selection. Assumed all public signups default to `LEARNER`; Mentor and Admin accounts are provisioned only via the admin "Add User"/"Add Mentor" actions, never self-registered.

16. **No dedicated learner resources hub.** `resources_lumoraspace`/`resources_mobile` are mentor-facing (nav item "Resources" under the mentor sidebar). No learner-facing equivalent screen exists — learners only see resources embedded inside a lesson or assignment. Assumed this is intentional (no standalone learner resources page in MVP), not a missing screen.

17. **Community links are static, not admin-managed.** No admin screen configures the Discord/Telegram links shown on `community_lumoraspace`/`community_mobile`. Assumed these are hardcoded app config, not database rows — this is the one learner-facing feature area with no matching admin CRUD screen anywhere in the export.

18. **Batch schedule as free text.** Schedule info appears inconsistently — `batches_mobile` shows "Mon, Wed, Fri • 18:00 EST", `batch_detail_forge_data_analyst_batch_04` shows only a date range with no days/time. Assumed `Batch.scheduleNote` is a free-text field rather than structured recurrence data, since no screen shows a structured day/time editor.

19. **Payment method as free text.** Values seen ("UPI Transfer", "Credit Card ending 4421", "Bank Transfer", "Online Payment") look like gateway-provided display strings rather than a fixed set. Assumed `Payment.method` is a string, not an enum — consistent with the MVP decision to stub the payment gateway rather than model Razorpay's actual method taxonomy.

20. **Certificate templates.** `certificates_lumoraspace_admin` shows "Templates: 3" as a stat but only ever renders detail for one ("Standard"). Assumed a `templateName` string on `Certificate` is sufficient for MVP rather than a separate `CertificateTemplate` model with real template management — revisit if the admin template editor becomes in-scope.
