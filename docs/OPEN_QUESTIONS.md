# Open Questions

All 20 questions from Phase 0 are resolved as binding decisions in `DECISIONS.md`. The three below are new — raised while applying those decisions to `DATA_MODEL.md` and reconciling `API.md` against them (Phase 0.5). Answer before implementation depends on the wrong assumption.

1. **`lumoraspace_home` vs. `student_dashboard_home`.** Both are LEARNER dashboards per `SCREEN_INVENTORY.md`, with overlapping fields (greeting, current-course card, progress stats) but different layouts — the same pattern as the already-resolved `student_progress`/`student_progress_lumoraspace` duplicate (`DECISIONS.md` Q12), which was never applied to this pair because `lumoraspace_home` was mismapped onto the public landing endpoint in the original `API.md` instead of being recognized as a learner-dashboard duplicate. No guess made: both currently sit on `GET /learn` in the corrected `API.md`. Pick one as canonical (or confirm they're deliberately different views, e.g. a compact vs. detailed dashboard) before building `/learn`.

2. **Program/batch selection sequencing relative to onboarding.** `DECISIONS.md` Q2 makes `Enrollment.programId` required, and the audit added `POST /programs/:id/enroll` for the "Enroll Now" CTA on `program_details_full_stack_developer` — but no screen shows *when* that happens relative to onboarding (`onboarding_welcome` → `onboarding_learning_goal` → `onboarding_experience_level` → `onboarding_success`). Does completing onboarding recommend/auto-select a program based on the stated goal, or is enrollment fully independent (learner browses `explore_programs` and enrolls separately, before or after onboarding)? `onboarding_success`'s "enrolled-course name" display only makes sense if the former, but nothing in the goal/experience-level screens captures a program choice. Needs a product decision, not a guess.

3. **Assignment screens aren't in the 16-screen MVP list, but the mentor "review submission" screen is.** AGENT_PROMPTS.md's MVP cut includes `review submission` (mentor grading a submission) but not `assignment_details_*`/`assignment_feedback_*` (the learner-facing screens that create and view the thing being reviewed). `API.md` keeps the learner assignment/submission endpoints because `review submission` has nothing to operate on otherwise — but whether the learner-facing screens themselves are in-scope for the first build milestone, or planned as a fast-follow immediately after, wasn't stated. Confirm before scoping M1.
