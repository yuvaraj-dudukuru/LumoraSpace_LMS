# Contracts reference

Compact index of the data layer so future sessions don't re-derive it. Signatures
reflect the code as of the pre-deploy hardening pass (2026-09-17). If this drifts
from the source, the source wins — update this file, not the other way round.

## 1. Functions

### `src/lib/auth-guards.ts`

| Signature | Returns | Outside request context? |
|---|---|---|
| `findCurrentUserById(userId: string): Promise<CurrentUser \| null>` | user row (no passwordHash) or null if missing/inactive | Yes — pure DB read |
| `findEnrollment(userId: string, programId: string): Promise<Enrollment \| null>` | the enrollment row, any accessState | Yes |
| `isEnrollmentGranted(enrollment: Enrollment \| null): boolean` | `accessState === GRANTED` | Yes — pure function |
| `isMentorForBatch(user: Pick<CurrentUser,"id"\|"role">, batchId: string): Promise<boolean>` | true if ADMIN, or MENTOR with a matching MentorAssignment | Yes |
| `getCurrentUser(): Promise<CurrentUser \| null>` | session user, re-fetched from DB, or null | **No** — calls `auth()` |
| `requireUser(): Promise<CurrentUser>` | user, else `redirect("/login")` | **No** |
| `requireRole(...roles: Role[]): Promise<CurrentUser>` | user, else `forbidden()` | **No** |
| `requireEnrollment(programId: string): Promise<Enrollment>` | caller's enrollment, else `forbidden()` | **No** |
| `requireGrantedEnrollment(programId: string): Promise<Enrollment>` | same, also requires GRANTED, else `forbidden()` | **No** |
| `requireMentorForBatch(batchId: string): Promise<CurrentUser>` | user, else `forbidden()` | **No** |

`CurrentUser = { id, name, email, role, onboardingComplete, streakDays }`. The `require*`
functions need `next/navigation`'s request context (`forbidden`/`redirect`) —
only the pure predicates above them are callable from a script (see
`scripts/verify-guards.ts`).

### `src/lib/queries/programs.ts`
- `getPublishedPrograms(): Promise<PublishedProgram[]>` — catalog grid, `status: PUBLISHED`. Server-only, no auth needed.
- `getProgramForCatalog(slug: string): Promise<ProgramForCatalog | null>` — program + outcomes + modules + lessons, no progress.
- `getEnrollableBatches(programId: string): Promise<EnrollableBatch[]>` — UPCOMING/ACTIVE batches with live seat counts. Does not check program status itself — only reached from the detail page after `getProgramForCatalog` already required PUBLISHED.
- `findOpenBatchForEnrollment(programId, batchId): Promise<{ id; capacity } | null>` — THE enroll rule, shared by `enrollAction` and `scripts/verify-enroll.ts`: the batch belongs to the program, is UPCOMING/ACTIVE, **and the program is PUBLISHED**. An ARCHIVED/DRAFT program can't be joined even with a batch id kept from before. Never consults existing enrollments — a GRANTED learner of an archived program keeps their content, because `requireGrantedEnrollment`/`resolveLessonProgram`/`getProgramProgress` never look at `Program.status` (proven by `verify-guards.ts` check 9 and `verify-enroll.ts`). `prisma/set-program-status.ts` is the only tool that changes a program's status; archiving also closes its UPCOMING/ACTIVE batches.

### `src/lib/queries/enrollments.ts`
- `getEnrollmentsForUser(userId: string): Promise<EnrollmentWithProgram[]>` — all enrollments + program + batch.
- `getEnrollmentWithProgram(enrollmentId: string): Promise<EnrollmentWithProgram | null>` — single lookup.

### `src/lib/queries/progress.ts` — THE shared calculation
- `getProgramProgress(enrollmentId: string): Promise<ProgramProgress>` — one query (nested module/lesson tree + completed LessonProgress +, per lesson, its linked Assessment's latest attempt for THIS enrollment +, per module, its Assignments' latest submission for this enrollment (M5a) — still one query, bounded nested selects, not a loop), then in-memory aggregation. `{ overallPercent, totalLessons, completedLessons, modules: ModuleProgress[] }`. Each `LessonProgressSummary` also carries `completedAt: Date | null` (Phase A — the enrollment's completion time, read from the same `lessonProgress` select, used to time `module_completed` activity), plus `assessmentId` and `attemptState: AttemptState | null` (M4.5) — `"not_attempted" | "in_progress" | "failed"`, or `null` when the lesson isn't a linked quiz OR is already `completed` (the existing checkmark already means "passed"; no separate badge then). Each `ModuleProgress` also carries `assignments: ModuleAssignmentSummary[]` (M5a) — `{ id, title, type, dueAt, state, score, maxScore }`, `state` one of `AssignmentSubmissionState = "not_started" | "submitted" | "under_review" | "revision_requested" | "reviewed"`. Assignment state is **not** folded into `totalLessons`/`completedLessons`/`overallPercent` — see Rules (D3).
- `findNextIncompleteLesson(progress: ProgramProgress): { moduleId; lesson } | null` — pure, no query.
- `flattenLessons(progress: ProgramProgress): LessonProgressSummary[]` — pure, no query; used for prev/next nav.

### `src/lib/progress-rollup.ts` — M4.5
- `refreshEnrollmentProgress(enrollmentId: string): Promise<ProgramProgress>` — THE rollup: `getProgramProgress` then caches `overallPercent` onto `Enrollment.progressPercent`. Both `markLessonComplete` and `submitAttempt`'s quiz-completion step call this instead of each inlining it — do not duplicate this logic a third time.

### `src/lib/queries/lessons.ts`
- `resolveLessonProgram(lessonId: string): Promise<{ programId; moduleId } | null>` — cheap lookup for guards, called BEFORE `requireGrantedEnrollment`.
- `getLessonDetail(lessonId: string, enrollmentId: string): Promise<LessonDetail | null>` — full content + this enrollment's notes/completed + `assessmentId` (M4.5, nullable). Call only after a guard produced `enrollmentId`. Does NOT itself fetch assessment details — callers with a non-null `assessmentId` call `getAssessmentOverview` separately (reused verbatim, not re-derived).

### `src/lib/queries/dashboard.ts`
- `getDashboardData(userId: string): Promise<DashboardData>` — `DashboardData` is `null` when the learner has no GRANTED enrollment that is ACTIVE **or COMPLETED** (render the empty state); an ACTIVE one is preferred, then most recent (Phase A widened this from ACTIVE-only so a learner who finished their only program still sees their certificate and module completions). Otherwise: learner name/streak, `ProgramProgress`, `learnerStatus` (from the enrollment's batch dates + status), `pendingWork` (unsorted `getPendingWork` result), next incomplete lesson, `nextStep` (`pickNextStep` over the pending work and the next lesson — the old nearest-`dueAt` assignment query is gone), and `recentActivity`: the newest `RECENT_ACTIVITY_LIMIT` (10) of six **derived** kinds — `lesson_completed` (LessonProgress.completedAt), `assignment_submitted` (Submission.submittedAt), `submission_reviewed` (Review.reviewedAt + outcome, same query), `assessment_submitted` (GRADED Attempt.submittedAt, with scorePercent/passed), `module_completed` (a module at 100% in the progress tree, timed by the latest `LessonProgressSummary.completedAt` of its lessons), `certificate_issued` (VALID certificates on the enrollment, in the enrollment select). Ties on the exact same instant rank the larger event first. Also `achievements` (`deriveAchievements`, see its entry). Queries: 1 (enrollment + certificates) → 1 (progress) → one parallel wave of 6 (pending work, lessons, submissions+reviews, graded attempts, distinct passed GRADED assessment ids, VALID certificate count) — 8 total in 3 waves. The page passes `requireUser()`'s `{ id, name, streakDays }` in; nothing here re-reads the user row.

### `src/lib/queries/pending-work.ts` — Phase A
- `getPendingWork(enrollmentId, now): Promise<PendingWorkItem[]>` — ONE query: the enrollment's program → PUBLISHED modules → every assignment (with this enrollment's latest real submission, NOT_STARTED excluded) + every PUBLISHED **GRADED** assessment (with this enrollment's attempts). `PendingWorkItem = { kind: "assignment" | "assessment", id, title, moduleTitle, moduleOrder, assignmentType, dueAt, estimatedMins, state, action, href }`. `state ∈ not_started | overdue | submitted | under_review | revision_requested | completed`; `action ∈ start | continue | view_feedback | resubmit`.
- Assignment derivation: no real submission → `overdue` when `dueAt < now`, else `not_started` (Start); SUBMITTED/UNDER_REVIEW → Continue (assignment page); REVISION_REQUESTED → Resubmit; REVIEWED → `completed`, View feedback → `/learn/submissions/{latest}`.
- Assessment derivation (`deriveAssessmentPending`, pure): **passed assessments are excluded** (any `passed === true`, or no threshold + any GRADED attempt — the quiz-completion rule). No attempts → Start; IN_PROGRESS → Continue → `/learn/attempts/{id}`; failed with attempts remaining → Resubmit; failed and exhausted → `completed` / View feedback → the latest graded attempt. Assessments have no due date (`dueAt: null`, rendered "No due date"); `estimatedMins` carries `timeLimitMins`.
- `sortPendingWork(items)` — pure: revision_requested → overdue → open items by `dueAt` asc (null last) → completed last; ties by module order, then title. Rendered by `components/pending-work-list.tsx`: `/learn` shows the top 3 **non-completed** items, `/learn/progress` shows all per course.

### `src/lib/queries/practice.ts` — Phase A
- `getPracticeAssessments(userId): Promise<PracticeProgramGroup[]>` — ONE query: PUBLISHED assessments with `kind: PRACTICE` in any program the learner has a GRANTED enrollment in, with the learner's attempts (matched by user — one enrollment per program in the MVP), grouped program → module (module order) in memory. Each item: `attemptsUsed` (SUBMITTED + GRADED), `allowedAttempts` (0 = unlimited), `bestScorePercent` (max over graded, null if none), `inProgress`, `attemptsExhausted`, `href` into the existing `/learn/assessments/[id]` flow. No page renders this any more (`/learn/practice` moved to `getPracticeActivities` below); it is kept because `scripts/verify-learner-dashboard.ts` step 7 still asserts it.
- `getPracticeActivities(userId, now): Promise<PracticeActivity[]>` — what `/learn/practice` renders. ONE query: every GRANTED enrollment → PUBLISHED modules → assignments (this learner's latest real submission) + PUBLISHED assessments of **both** kinds (this learner's attempts, question count). Flat list; `kind ∈ quiz (PRACTICE assessment) | assessment (GRADED) | assignment | project (Assignment.type)`; `status ∈ in_progress | revision_requested | overdue | not_started | not_passed | under_review | completed`. Sorted most-urgent-first in exactly that order (then program, module order, title), so the page's "Next Up" is simply the first item for which `isActionablePractice(status)` is true (everything up to `not_passed`).
- `derivePracticeAssessment` / `derivePracticeAssignment` — pure; they **wrap** `deriveAssessmentPending` / `deriveAssignmentPending` (above) instead of re-deriving state, so the hub and the pending-work list can't disagree. Differences from pending work, all deliberate: a passed assessment is listed as `completed` (pending work drops it); `completed` links "Review" to the latest finished attempt and exposes `retakeHref` (the overview page) while attempts remain; an `IN_PROGRESS` attempt wins over an earlier pass (`in_progress`, so a retake temporarily leaves the completed count); SUBMITTED/UNDER_REVIEW assignments read `under_review` and link "View Submission" to `/learn/submissions/{id}`. "x of y activities completed" counts `completed` only.

### `src/lib/queries/certificates.ts`
- `getCertificatesForUser(userId: string): Promise<LearnerCertificate[]>`.
- `getCertificateDetailForUser(certificateId: string): Promise<CertificateDetailForUser | null>` — includes `userId` *only* so the `[id]` page can verify ownership before rendering; the page must `forbidden()` when `userId` doesn't match the caller.
- `getCertificateForVerification(certificateNumber: string): Promise<VerifiedCertificate | null>` — backs the PUBLIC `/verify/[certificateNumber]` route. Returns **exactly** `{ learnerName, programName, issuedAt, status }`, nothing else — never add `userId`/email/batch/enrollment fields to this query or its return type.

### `src/lib/shuffle.ts` — pure, no DB
- `seededShuffle<T>(items: T[], seed: string): T[]` — string-hash → mulberry32 PRNG → sort-key shuffle. Same `seed` always reproduces the same permutation.

### `src/lib/queries/assessments.ts`
- `resolveAssessmentProgram(assessmentId: string): Promise<{ programId; moduleId } | null>` — cheap lookup for guards, called BEFORE `requireGrantedEnrollment`. Mirrors `resolveLessonProgram`.
- `getAssessmentOverview(assessmentId: string, enrollmentId: string): Promise<AssessmentOverview | null>` — title/time-limit/question-count/`allowedAttempts` + this enrollment's finished-attempt count + an in-progress attempt id if one exists + (M4.5) `programId`/`programName`/`moduleTitle`/`lesson: {id,title} | null` for breadcrumbs. Powers the pre-attempt page AND the lesson page's QUIZ content (reused as-is, not re-derived).
- `getAttemptForGuard(attemptId: string): Promise<AttemptGuardInfo | null>` — one query joining the attempt to its assessment/module/program + (M4.5) `lessonId: string | null` if the assessment is linked to a quiz lesson; used by every attempt-scoped action AND the attempt page to decide ownership, expiry, and which view to render.
- `getLiveAttemptQuestions(assessmentId, attemptId, shuffle): Promise<LiveAttemptQuestion[]>` — questions in **seeded-shuffle order** (see Rules below) merged with saved `Answer` rows. Never selects `isCorrect`/`explanation` from the DB — not merely hidden client-side, actually absent from the query, for an IN_PROGRESS attempt.
- `getGradedAttemptQuestions(assessmentId, attemptId, shuffle): Promise<GradedAttemptQuestion[]>` — same, but includes `isCorrect`/`explanation`. Callers only invoke this when `Assessment.showResultsImmediately` is true.

### `src/lib/queries/assignments.ts` — M5a
- `resolveAssignmentProgram(assignmentId: string): Promise<{ programId; moduleId } | null>` — mirrors `resolveAssessmentProgram`.
- `getAssignmentDetail(assignmentId: string, enrollmentId: string): Promise<AssignmentDetail | null>` — assignment + requirements/instructions (parsed `Json`) + resources + rubric criteria (shown BEFORE submitting) + this enrollment's **real** submission history (`status !== NOT_STARTED`, ordered by `attemptNumber` asc).
- `nextAttemptNumber` / `canSubmitNewAttempt` — pure, no DB. The single source of truth for "can this learner submit right now", shared by the assignment page's render decision and `submitAssignment`'s guard — never duplicated. See Rules for the exact rule (NOT_STARTED handling, REVISION_REQUESTED vs `maxAttempts`).
- `getSubmissionWithReview(submissionId: string): Promise<SubmissionWithReview | null>` — submission + assignment title + the owning enrollment's `userId` (the ownership check, in the same query) + review with mentor name and rubric scores joined to their criteria.

### `src/lib/queries/activity.ts`
- `getLearningHoursStats(userId: string): Promise<LearningHoursStats>` — `{ totalHours, weeklyActivity }`, see Known Gaps.

### `src/lib/queries/mentor.ts` — M5b
- `getMentorBatchIds(user): Promise<string[]>` — ADMIN gets every `Batch.id` in the system; MENTOR gets only batches with a `MentorAssignment` row. Resolved **once**, here — every other function in this file takes the resulting array as a plain `batchIds` argument and filters by it; none of them branch on role themselves. Empty array is a normal, handled case throughout (new mentor, no assignment yet), not an error.
- `getMentorDashboard(batchIds)` — pending review count, at-risk learners (see Rules), upcoming due dates (assignments in the *programs* the batches belong to, future `dueAt`), recent submission activity.
- `getReviewQueue(batchIds, filter: "all" | "pending" | "under_review" | "reviewed" | "revision_requested")` — `"all"` is every status except `NOT_STARTED`; oldest-first (`submittedAt asc`) always.
- `getSubmissionForReview(submissionId)` — submission + learner (no `passwordHash`) + assignment + requirements + rubric criteria + prior real submissions on the same assignment + the `Review` **as-is**, including which mentor's draft it is. Returns `batchId` for the caller's `requireMentorForBatch`. See Rules for why redaction of another mentor's draft happens in the page, not here.
- `getMentorLearners(batchIds, query?: { search?; status?: "all" | "needs_attention" })` — roster rows, reusing `Enrollment.progressPercent` (already kept correct by `refreshEnrollmentProgress`) rather than recomputing it per row. Each row also carries `learnerStatus` (Phase A) from `deriveLearnerStatus` — the roster pill is "Needs Attention" when `needsAttention`, else the pace label.
- `getLearnerDetail(userId, batchIds)` — `null` when the learner has no enrollment in any batch the caller can see, whether because the batch access doesn't extend that far or because the `userId` doesn't exist at all — both cases must look identical, never leaking which one it was.
- `NEEDS_ATTENTION_STALE_DAYS` (= 7) — exported constant, see Rules.
- Internal `getBatchEnrollmentsWithActivity` — one query (bounded nested `lessonProgress`/`submissions`/`attempts` selects per enrollment, same shape as every other milestone's progress queries), shared by `getMentorDashboard` and `getMentorLearners` so "what counts as at-risk" is one rule, not two.

### `src/lib/validations/review.ts` — M5b
- `validateRubricScoreEntries(submitted, criteria)` — pure, no DB. Rejects a `criterionId` that doesn't belong to this assignment's rubric, a duplicate entry, or any score outside `0..maxScore`. A draft may legitimately be partial, so this alone is what `saveReviewDraft` uses.
- `validateRubricScoresComplete(submitted, criteria)` — everything above, plus every criterion must be present. `submitReview` uses this — a final decision needs a non-partial total.

### `src/lib/queries/admin.ts` — M5c
- `getAdminDashboardStats(): Promise<AdminDashboardStats>` — 5 direct, unscoped counts (total learners, active enrollments, AWAITING enrollments, pending reviews platform-wide, certificates issued all-time). No `batchIds` threading like M5b's mentor queries — this route is already `requireRole(ADMIN)`-only, so there's nothing to scope.
- `getEnrollmentsForAdmin(filter?: { accessState?; status?; search? })` — every enrollment + learner/program/batch/progress. Sorted AWAITING-first in JS after the query (Prisma `orderBy` can't express "this enum value first").
- `getUsersForAdmin(filter?: { role?; search? })` / `getUserDetailForAdmin(userId)` — the latter includes `mentorAssignments` regardless of the user's role (empty array for a non-mentor) — the PAGE decides whether to render the batch-assignment section, same posture as M5b's draft redaction.
- `getAllBatchesForAdmin()` — every batch, for the "assign mentor" dropdown.
- `getCertificatesForAdmin(filter?: { status?; search? })` / `getCertificateDetailForAdmin(id)`.
- `getProgramsForAdmin(filter?: { status?; search? }): Promise<{ counts, rows }>` — `counts` (total/published/draft/archived) are platform-wide and ignore the filter; `rows` follow it (search matches name or description), newest `updatedAt` first. `activeBatchCount` counts `ACTIVE` batches only; `enrollmentCount` is every enrollment row.
- `getProgramDetailForAdmin(id)` — one query, everything else derived in JS. `mentorCount` is the distinct union of mentors across the program's batches (DECISIONS.md #7). `curriculum.practiceActivityCount` = `PRACTICE` assessments + assignments (what the learner practice hub lists); `gradedAssessmentCount` = `GRADED` assessments. `openBatchCount` = `UPCOMING` + `ACTIVE` batches, i.e. what archiving would also archive. `recentBatches` is capped at 4, newest start date first.
- `setProgramStatus(id, { status })` (`src/app/admin/programs/[id]/actions.ts`) — `requireRole(ADMIN)`, `setProgramStatusSchema`. **Mirrors `prisma/set-program-status.ts` exactly**: archiving also archives the program's `UPCOMING`/`ACTIVE` batches in the same transaction; nothing is deleted; `Enrollment` is never touched; un-archiving (→ `DRAFT`) does not restore batches. Change one, change the other.

### Admin area — shared pieces
- `src/lib/action-result.ts` — `ActionResult = { ok: true; redirectTo? } | { ok: false; error }`, the return type of every admin Server Action added since. `FormAction` is a FormData-taking action.
- `src/components/admin/modal-form.tsx` (client) — a button that opens a dialog around **server-rendered, uncontrolled** fields (`components/admin/fields.tsx`) and calls a FormData Server Action; closes + `router.refresh()` on `ok`, follows `redirectTo`, shows `error` and keeps what was typed otherwise. `action-button.tsx` (client) — one click → one pre-bound Server Action, with an optional inline confirm step. These two are why the admin pages are almost entirely Server Components.
- `src/lib/validations/admin-content.ts` — Zod schemas for every admin form. They parse `formObject(formData)`, so the helpers there normalise FormData's quirks: `""` → `undefined` for optional fields, string → number, checkbox `"on"` → boolean. `parseQuestionForm` reads the repeated `optionText` inputs and the `correct` radio index; `questionSchema` enforces per-type rules (a choice question must have ≥ 2 non-empty options and a correct one).
- `src/lib/pagination.ts` — `paginate(rows, rawPage)` slices **in memory** (10 per page) after the query returned the whole filtered list; fine for cohort-sized tables, replace with `skip`/`take` if one can reach thousands. `buildHref(path, params, defaults)` builds filter links, dropping defaults.
- `src/lib/csv.ts` — `csvResponse(stem, rows)`; every cell quoted, and a leading `= + - @` prefixed with `'` (spreadsheet formula injection). Used by both export routes.
- `src/components/admin/line-chart.tsx` (client) — the only chart. Up to three count series on ONE y-axis, colours `--color-series-1..3` in fixed order (validated for colour-vision separation; the older `--chart-*` tokens are three near-identical violets and are not used). Always renders a legend and a "View as table" fallback.
- `src/components/shell/app-shell.tsx` — optional `topBar` prop (admin only): a GET search form → `/admin/search?q=` and a bell → the inbox with the unread count the layout fetched. The active nav item is the **longest** matching href, so `/admin` isn't also highlighted on `/admin/users`.

### `src/lib/notifications.ts` + `src/lib/queries/notifications.ts` + `src/lib/actions/notifications.ts`
- `notify(userIds, { type, title, body, actionUrl? })` / `notifyAdmins(input)` — **the only writers of `Notification` rows**, in-app only (email stays in `mail.ts`). Like `mail.ts` they never throw: a notification is a side effect of an action that already committed. `notify` skips anyone whose `NotificationPreference` switches that type off (`ACCESS_GRANTED` → `courseUpdates`, `ASSIGNMENT_FEEDBACK` → `feedbackNotifications`, `ANNOUNCEMENT` → `systemNotifications`; no row = everything on; admin-facing types have no switch). `actionUrl` is always an app-relative path; the inbox refuses to render anything else as a link.
- Written from: `enrollAction` → admins (`ENROLLMENT_REQUEST`); `grantAccess` / `bulkGrantAccess` / `createEnrollment` with grant → learner (`ACCESS_GRANTED`); `submitReview` → learner (`ASSIGNMENT_FEEDBACK`); `refundPayment` → admins (`PAYMENT_REFUNDED`); `sendAnnouncement` → learners (`ANNOUNCEMENT`).
- `getNotificationsForUser(userId, "all" | "unread")` (newest 100), `getUnreadNotificationCount(userId)`, `groupNotificationsByDay(items, now)` (pure: Today / Yesterday / Earlier).
- `markNotificationRead(id)` / `markAllNotificationsRead()` — `requireUser`, and the `updateMany` is filtered on the caller's own id, so another user's notification id matches nothing.

### `src/lib/queries/admin-batches.ts`, `admin-mentors.ts`, `admin-options.ts`, `search.ts`
- `getBatchesForAdmin({ status?, search? })` → `{ counts, rows }` (counts platform-wide). `getBatchDetailForAdmin(id)`. **"Learners" on a batch = seat-holding enrollments (not `CANCELLED`/`DROPPED`)** — the same rule `enrollAction` uses for capacity.
- `getMentorsForAdmin({ view?, search? })` → `{ counts, rows }`. Only `UPCOMING`/`ACTIVE` batches count as current work: *assigned* = ≥ 1 current batch, *available* = `ACTIVE` account with none. `workloadFor(learnerCount)` is `learners ÷ MENTOR_FULL_LOAD_LEARNERS` (30 — a constant, because no capacity field exists on a mentor) → Low < 40% ≤ Moderate < 80% ≤ High.
- `admin-options.ts` — option lists for dialog selects (`getProgramOptions`, `getMentorOptions`, `getLearnerOptions`, `getOpenBatchOptions`, `getModuleOptions`); archived programs are excluded everywhere new content could be attached.
- `searchAdmin(q)` — users / programs / batches, case-insensitive contains, 8 per group, nothing below 2 characters.

### `src/lib/queries/admin-curriculum.ts`, `admin-assessments.ts`
- `getCurriculumForAdmin(programId)` — modules → lessons (+ linked assessment, `progressCount`), assessments, assignments, counts, `totalMinutes`, and `issues` from `validateCurriculum` (pure). The validation panel reports only things a learner would actually hit, grouped by kind: no modules / none published, module with no lessons, quiz with no assessment, quiz whose assessment has no questions or isn't published, video with no URL, reading with no content. "No issues detected" means none of *those*.
- `getAssessmentsForAdmin({ status?, programId?, search? })`, `getAssessmentForBuilder(id)` — **the one place correct answers are read for display; never reuse on a learner page.** `autoGradedMarks` excludes `CODE_SNIPPET`.

### `src/lib/queries/admin-analytics.ts`
- `getAdminDashboard(rangeDays, now)` and `getAdminAnalytics(rangeDays, now)` (ranges 7 / 30 / 90). **Everything is derived from existing rows — there is no analytics/event table**, so no page views, sessions or time spent. "Activity" = completed a lesson, submitted an assignment, or started an attempt (the same three signals as the mentor "last active"). Trends compare with the previous equal period and are `null` when that period was empty; completion rate has no history, so no trend. `buildBuckets` gives 7–10 chart points per range. Alerts: module drop-off (a module's completed-lesson share ≥ `DROP_OFF_POINTS` = 15 below the module before it, worst one per program), review backlog (> `REVIEW_BACKLOG_HOURS` = 48), active learners in a mentorless batch, enrollments awaiting access.

### `src/lib/queries/payments.ts` — admin payments (records only; gateway still stubbed)
- `transactionRef(orderId): string` — pure. `ORD-2026-00124` → `TXN-2026-00124`. There is no transaction-number column; the label shown in the UI is the unique `orderId` under the design's prefix.
- `getPaymentStats(rangeDays: 7 | 30 | 90): Promise<PaymentStats>` — revenue = sum of `SUCCESSFUL` amounts created inside the range; `revenueChangePercent` compares with the equally long period just before and is `null` when that period had no revenue (the UI then hides the trend line rather than showing a made-up one); successful/pending/refund counts are by `createdAt` inside the range. Amounts are summed as a single currency (the newest payment's) — a second currency needs per-currency totals first.
- `getPaymentsForAdmin(filter?: { status?; search? })` — newest first; `search` matches learner name, email, or order id (a typed `TXN-…` is matched against `ORD-…`). `programName` is `null` when the payment has no enrollment.
- `getPaymentDetailForAdmin(id)` — payment + learner + linked enrollment (`null` if none) + `events` oldest first.
- `refundPayment(id, { reason })` (`src/app/admin/payments/[id]/actions.ts`) — `requireRole(ADMIN)`, `refundPaymentSchema`. Only `SUCCESSFUL → REFUNDED`; sets `refundedAt` and appends a `REFUNDED` `PaymentEvent` carrying the reason, in one transaction guarded by `updateMany({ status: "SUCCESSFUL" })` so a double click writes one event. **Moves no money and never touches the `Enrollment`** — access is suspended separately on `/admin/enrollments`.

### `src/lib/format.ts`
- `formatRelativeTime`, `formatDate`, `formatDateTime` (short date + time), `formatMoney(amount, currency)` — `Intl.NumberFormat("en-IN")`, no decimals on whole amounts.

### `src/lib/validations/admin.ts` — M5c
- `updateEnrollmentStatusSchema`, `createUserSchema`, `updateUserRoleSchema`, `setUserStatusSchema`, `assignMentorSchema`, `revokeCertificateSchema`, `refundPaymentSchema` (reason 1–300 chars), `resetUserPasswordSchema` (`newPassword` ≥ 8) — Zod, mirror the existing per-domain validation files. `createUserSchema` (like `signupSchema`, `loginSchema`, the Credentials `authorize()` schema and the bootstrap env schema) **trims and lowercases** the email — `User.email` is unique and every lookup normalises the same way.
- `resetUserPassword(userId, newPassword)` (`src/app/admin/users/actions.ts`) — `requireRole(ADMIN)`, Zod, bcrypt cost 10, sets `passwordHash` (works for an OAuth-only account too, deliberately). The **only** password-reset path: there is no self-service forgot-password flow (no reset-token model in the schema); `/login` says "Forgot your password? Contact your program admin."
- `wouldSelfDemote(callerId, targetUserId, newRole): boolean` / `wouldSelfDeactivate(callerId, targetUserId, newStatus): boolean` — pure, no DB. Both `true` only when `callerId === targetUserId` and the change would remove the caller's own ADMIN/ACTIVE state. See Rules for why both exist.

### `src/lib/certificates.ts` — M5c, tightened pre-deploy
- `issueCertificateIfEligible(enrollmentId): Promise<Certificate | null>` — idempotent. Re-fetches the enrollment fresh (never trusts a caller-supplied percent); `null` unless `progressPercent === 100`; `null` if a certificate of **any status** (`VALID` or `REVOKED`) already exists for that `enrollmentId` — a revocation sticks, the rollup never re-issues. Otherwise sets `Enrollment.status = COMPLETED` + `completedAt`, generates the next `LUM-{year}-{00001..}` number, and creates the certificate — retrying the create once on a `P2002` sequence-number collision. Only called from `refreshEnrollmentProgress`, and only on the `<100 → 100` transition (see Rules).

### `src/lib/storage.ts` — uploads (Cloudflare R2 / any S3-compatible bucket)
- `isStorageConfigured(): boolean` — all four required `S3_*` vars present (`S3_REGION` is optional, defaults to `"auto"`). The assignment page checks this server-side and passes `fileUploadEnabled` down; the upload control is not rendered otherwise.
- `sanitizeFileName(raw): string` — pure. Basename only (no `/` or `\`), whitespace → `-`, only `[A-Za-z0-9._-]`, `..` collapsed, no leading dot/dash, 100-char cap keeping the extension, never empty.
- `getPresignedUploadUrl(fileName, fileType, fileSize): Promise<{ uploadUrl, publicUrl, key }>` — presigned PUT, 5-min expiry, `ContentType`/`ContentLength` signed in. Key is `assignment-submissions/{uuid}-{sanitized name}`. `publicUrl` is `${S3_ENDPOINT}/${bucket}/${key}` and is what gets stored in `Submission.fileUrl` — it is an **identifier, not a readable link** (objects are private).
- `storageKeyFromUrl(fileUrl): string | null` — inverse of the above; `null` for anything not on our bucket/prefix (or when storage is unconfigured — never matches an `undefined/undefined/` prefix).
- `isKnownStorageUrl(url): boolean` — `storageKeyFromUrl(url) !== null`; what `submitAssignment` uses to reject an off-bucket `fileUrl`.
- `getPresignedDownloadUrl(key): Promise<string>` — presigned GET, 5-min expiry. Throws when storage is unconfigured; callers catch.
- Allowed types (`validations/assignment.ts`): PDF, PNG, JPEG, `.doc`, `.docx`; 10 MB max.

### `src/lib/submission-file.ts`
- `getSubmissionFileLink(fileUrl: string | null): Promise<SubmissionFileLink | null>` — `{ kind: "ready", href, fileName } | { kind: "unavailable", fileName } | null`. Presigns a download for our own bucket URLs, degrades to `"unavailable"` (logged) if presigning fails, passes a non-bucket URL (seed placeholders only) through as-is. Called **only after** the page's guard has passed — see Rules — and rendered by `components/submission-file-link.tsx`.

### `src/lib/mail.ts` — the ONLY email entry point
- `sendAccessGrantedEmail(to, { learnerName, programName })`, `sendAssignmentReviewedEmail(to, { learnerName, assignmentTitle, outcome, submissionId })` — both `Promise<void>`, both **never throw**. Every link is absolute, built here from `APP_URL` (`/login`, `/learn/submissions/{id}`); callers never assemble URLs. If `APP_URL` is unset or not an absolute `http(s)` URL the send is `console.warn`-ed and skipped. Resend errors are logged, never thrown. `src/lib/email.ts` only holds the lazy Resend client.

### `src/lib/learner-status.ts` — pure, no DB (Phase A)
- `LearnerStatus = "NOT_STARTED" | "ON_TRACK" | "BEHIND" | "COMPLETED"`, `ON_TRACK_TOLERANCE_PERCENT = 10`.
- `elapsedPercent(batchStart, batchEnd, now): number` — 0..100, clamped; 100 when `end <= start`.
- `deriveLearnerStatus({ batchStart, batchEnd, now, progressPercent, enrollmentStatus }): LearnerStatus` — in order: enrollment `COMPLETED` or progress ≥ 100 → COMPLETED; `now < batchStart` → NOT_STARTED; progress ≥ elapsed − 10 → ON_TRACK; else BEHIND. Callers pass `now`. Rendered by `components/learner-status-pill.tsx` (`LEARNER_STATUS_LABEL` + one style map) on `/learn`, `/learn/progress` and `/mentor/learners`. Checked without a DB by `scripts/verify-learner-logic.ts`.

### `src/lib/next-step.ts` — pure, no DB (Phase A)
- `DUE_SOON_DAYS = 3`; `pickNextStep(pending: PendingWorkItem[], nextLesson, now): NextStep` — revision requested (Continue) → overdue (Start) → an assignment with nothing submitted due within 3 days (Start) → the next incomplete lesson (Start) → `null`. Ties by due date, then module order. Assessments never become the next step (no due date to rank by). Lessons always say "Start": the progress tree carries no "started" signal. Consumed only by `getDashboardData`; checked without a DB by `scripts/verify-learner-logic.ts`.

### `src/lib/achievements.ts` — pure, no DB (Phase A)
- `deriveAchievements({ streakDays, progress, passedGradedAssessmentCount, validCertificateCount }): Achievement[]` — exactly four kinds, `streak | modules_completed | graded_assessments_passed | certificates`, each `{ kind, count, label }`; zero-count kinds are omitted, labels are built from the count only. Modules completed = modules at 100% with ≥ 1 lesson. Consumed only by `getDashboardData`.

### `src/lib/streak.ts` — pure, no DB
- `STREAK_TIMEZONE = "Asia/Kolkata"` — the one fixed zone that defines "a day".
- `calendarDayIndex(at: Date): number` — days since epoch of the local calendar day `at` falls on in that zone.
- `nextStreakState({ streakDays, lastActiveAt }, now): { streakDays, lastActiveAt }` — no previous activity → 1; same day → unchanged (min 1); next day → +1; longer gap → 1. `lastActiveAt` always becomes `now`.

### `src/lib/validations/settings.ts` + `src/app/learn/settings/actions.ts`
- `updateProfileSchema` (`name` 1..120, `bio` ≤ 500 optional), `changePasswordSchema` (`currentPassword`, `newPassword` ≥ 8, `confirmNewPassword` must match).
- `updateProfile(input)` / `changePassword(input)` — `requireUser()` only (any role, DECISIONS Q9); both touch only the caller's own row via the session id, never a client-supplied id. `changePassword` refuses for an OAuth-only account (`passwordHash === null`) with a named error; bcrypt cost 10. Rendered by both `/learn/settings` and `/mentor/settings`.

### `prisma/bootstrap-schema.ts` — not `src/lib`, but a contract all the same
- `validateBootstrapData(raw: unknown): { success: true; data } | { success: false; issues: string[] }` — pure (no DB/fs/exit). File shape `{ _template?: boolean, programs: [ { program, modules, assessments, assignments, batches } ] }`. The `superRefine` enforces: valid ISO dates with `endDate > startDate` (and `dueAt`), every `moduleOrder`/`linkedLessonId` resolves, linked lessons are `QUIZ` and linked once, every `QUIZ` lesson has an assessment, unique lesson ids / module orders / program slugs, `MULTIPLE_CHOICE`/`TRUE_FALSE` have ≥ 1 correct option, `CODE_SNIPPET` options optional. Both bootstrap scripts run it **before any DB call** and refuse `_template: true`. Checked without a DB by `scripts/verify-bootstrap-data.ts`.

## 3. Rules

- **All progress percentages come from `getProgramProgress`.** No page computes its own — if a screen needs a percentage, it calls this (or reuses an already-fetched `ProgramProgress`).
- **Every Server Action re-verifies enrollment server-side.** IDs in the request (lessonId, programId, batchId) are attacker-controlled — never trust them without re-resolving and re-checking `requireGrantedEnrollment`/`requireRole` inside the action itself, even if the calling page already checked.
- **Learning hours and weekly activity are DERIVED, not tracked.** `getLearningHoursStats` sums `Lesson.durationMins` over completed lessons — there is no time-tracking model. Label this honestly in UI copy ("Est. Learning Hours"), never as measured time.
- **Streak comes from `User.streakDays`** — a stored counter, written in exactly one place: `markLessonComplete` (via `nextStreakState`, `src/lib/streak.ts`), by calendar day in the fixed `STREAK_TIMEZONE` (`Asia/Kolkata`): same day = unchanged, next day = +1, any longer gap = reset to 1. `submitAttempt`'s quiz completion does **not** touch it. Any screen showing a streak reads the stored field (via `requireUser()`'s `CurrentUser` or a direct `user.streakDays` select), never recomputes it.
- **Shuffled question order is derived, not stored.** There is no `Attempt.questionOrder` column. `getLiveAttemptQuestions`/`getGradedAttemptQuestions` run `seededShuffle(questions, attemptId)` when `Assessment.shuffleQuestions` is true — `attemptId` never changes after creation, so the same order comes back on every load with zero persisted state. Do not add a stored-order column without removing this derivation (they'd disagree).
- **The attempt deadline is always recomputed server-side** as `Attempt.startedAt + Assessment.timeLimitMins`, never read from the client. `/learn/attempts/[attemptId]`'s page checks this on every load and grades-in-place (calls the same `submitAttempt` the Submit button calls) if it's already passed, before rendering anything. The client's countdown is cosmetic.
- **`CODE_SNIPPET` questions are never auto-graded.** `submitAttempt`'s grading sums `Question.points` only over `MULTIPLE_CHOICE`/`TRUE_FALSE`; a `CODE_SNIPPET` answer's `freeTextAnswer` is stored but contributes nothing to `scorePercent`. `status` still becomes `GRADED` — there is no "awaiting manual review" `AttemptStatus`. A future grading UI would query `GRADED` attempts' `Answer` rows where `Question.type = CODE_SNIPPET`.
- **File uploads go direct-to-bucket via presigned URLs, and the bucket is private.** The learner's browser PUTs to a 5-minute presigned URL from `getAssignmentUploadUrl` (which re-runs `requireGrantedEnrollment` and re-validates type/size — the signature binds `ContentType`/`ContentLength`). `submitAssignment` accepts the resulting `fileUrl` only if `isKnownStorageUrl` says it's on our bucket. Nothing ever renders `Submission.fileUrl` as an `href`: both submission pages call `getSubmissionFileLink` **after** their guard (`requireMentorForBatch` / the ownership check) to mint a 5-minute presigned GET at render time, so the link is never generated for someone who can't see the submission. The upload control is rendered only when `isStorageConfigured()` is true server-side (`fileUploadEnabled` prop) — the client never sees the `S3_*` vars. A file-only submission is real submitted work; the "No submitted work on file" state checks `githubUrl || notes || file`.
- **Achievements are derived, four kinds only (Phase A).** Streak (`User.streakDays`), modules completed (progress tree), graded assessments passed (distinct GRADED assessments with a `passed` attempt for the enrollment), certificates (the learner's VALID certificates, all programs). There is no badge model; do not add a fifth kind without a real field behind it.
- **"Published assignment" means "assignment in a PUBLISHED module" (Phase A).** `Assignment` has no status column, so `getPendingWork` filters on `Module.status` instead. `getProgramProgress` deliberately does not filter modules (a learner's curriculum tree is whatever the program has); only the pending-work list applies the module filter.
- **Assignments are module-level (M5a, D2).** `Assignment` has no `Lesson` FK — deliberately not added, unlike `Lesson.assessmentId`. They render as an "Assignments" section inside each expanded `CurriculumAccordion` module, not attached to a specific lesson.
- **Assignment state never touches `Enrollment.progressPercent` (M5a, D3).** Progress stays lesson-based. `submitAssignment` never calls `refreshEnrollmentProgress`.
- **A `NOT_STARTED` `Submission` row is a seed placeholder, not a real attempt (M5a).** The seed creates one for Priya Sharma / Data Cleaning Assignment to demonstrate "nothing submitted yet" as real DB state rather than an absent row. It's excluded from `getAssignmentDetail`'s history, excluded from attempt counting, and can never coexist with a real row for the same assignment+enrollment — `submitAssignment` `upsert`s onto its exact `attemptNumber` slot (converting it in place) instead of colliding with it via a plain `create`.
- **`REVISION_REQUESTED` bypasses `maxAttempts` entirely (M5a).** `canSubmitNewAttempt` (`queries/assignments.ts`) blocks a new submission only when the latest is `SUBMITTED`/`UNDER_REVIEW`; when it's `REVISION_REQUESTED`, a new attempt is always allowed regardless of how many real attempts already exist — a mentor asking for a revision isn't the same thing as the learner spending their own attempts. The numeric cap applies only when the latest is `REVIEWED` (or there's no submission yet). Confirmed intentionally: the seed's Marcus Wei fixture has `maxAttempts: 1` already used by a `REVISION_REQUESTED` submission and is expected to still be resubmittable.
- **`dueAt` is informational only (M5a).** A late submission is accepted; the assignment page just shows a "Past Due" flag. `submitAssignment` never blocks on it.
- **Mentors see only their assigned batches; admins see all of them (M5b).** Resolved once, at `getMentorBatchIds` — every other mentor query takes the resulting `batchIds: string[]` as a plain argument and filters `batchId: { in: batchIds }`. None of them re-check `role`; an admin's wider array flows through the identical filter as a mentor's narrower one. The one exception is submission-scoped (not list-scoped) access: `/mentor/submissions/[id]` calls `requireMentorForBatch(submission.batchId)` directly, which already special-cases `ADMIN` in `isMentorForBatch`.
- **Mentor-facing "last active" is derived, not read from `User.lastActiveAt` (M5b).** `User.lastActiveAt` IS now written — by `markLessonComplete` only, alongside the streak — but the mentor queries deliberately don't read it: mentor-facing "last active" stays `MAX(LessonProgress.completedAt, Submission.submittedAt, Attempt.startedAt)` per enrollment, because that also counts quiz attempts and submissions, which don't move `lastActiveAt`. Same "derived not tracked" posture as Learning Hours. A learner with zero activity signals shows as `null`/"no activity yet", which counts as maximally stale for the at-risk rule below, not as an error.
- **Learner pace status is one derived function on three screens (Phase A).** `deriveLearnerStatus` (`src/lib/learner-status.ts`) compares progress with how far the batch calendar has elapsed. `/learn` and `/learn/progress` feed it `getProgramProgress().overallPercent`; the mentor roster feeds it the cached `Enrollment.progressPercent` it already displays (kept correct by `refreshEnrollmentProgress`). It is **not** the at-risk rule below — the roster shows "Needs Attention" when that rule fires and the pace status otherwise. Nothing stores the status; it is recomputed with `now` on every render.
- **At-risk thresholds (M5b):** `NEEDS_ATTENTION_STALE_DAYS = 7` — no activity in 7+ days (or ever) flags a learner on the dashboard and the roster's "Needs Attention" filter, alongside a failed assessment attempt or an outstanding `REVISION_REQUESTED` submission (only the *latest* attempt per assessment/assignment counts — an old fail later passed, or an old revision-request later resubmitted, isn't a standing problem). Separately, `/mentor/submissions`' queue urgency threshold is a fixed 6 days, per spec — deliberately a different number for a different purpose, not reusing the 7-day constant.
- **Claiming a submission for review tracks ownership via `Review.mentorId`, since `Submission` has no reviewer column (M5b).** `claimForReview` upserts a draft `Review` (`mentorId: caller`, no `outcome`/`reviewedAt`) at the moment `SUBMITTED → UNDER_REVIEW`. Idempotent for the same mentor; a different mentor's existing claim blocks with a named error. A pre-existing `UNDER_REVIEW` row with **no** `Review` at all (the seed's Aisha Patel fixture predates this milestone's ownership concept) is treated as claimable/adoptable, not permanently stuck — the alternative would be a dead end no mentor could ever resolve.
- **Never returning another mentor's draft feedback is enforced by the page, not the query (M5b).** `getSubmissionForReview` fetches `Review` as-is, including whose draft it is — the grading page compares `review.mentorId` to the signed-in mentor before deciding what to render: someone else's in-progress draft (`outcome === null`) renders as "currently being reviewed by {name}" with the feedback/score fields never interpolated into the returned JSX. A **finalized** review (`outcome` set) is visible to any mentor with batch access, same as the learner already sees it. Same mechanism as hiding quiz answers (M4.5) and another learner's submission (M5a) — the data never reaches the client because the page never threads it into what's rendered, not because the query omitted it.
- **Rubric scores are validated server-side regardless of the client's `min`/`max` input attributes (M5b).** `validateRubricScoreEntries` rejects a `criterionId` from a different assignment and any score outside `0..maxScore`; `saveReviewDraft` uses this alone (a draft may be partial). `validateRubricScoresComplete` additionally requires every criterion to be scored; `submitReview` uses this since a final decision's computed total must never be partial.
- **An admin cannot lock themselves out (M5c).** `updateUserRole` blocks a caller from changing their own role away from `ADMIN` (`wouldSelfDemote`) — the task's explicit ask, since `updateUserRole` is itself `requireRole(ADMIN)`-gated and a role change is otherwise irreversible from inside the app. `setUserStatus` carries the identical guard for self-deactivation (`wouldSelfDeactivate`) — not explicitly asked for, but the same lockout risk (`findCurrentUserById` returns `null` for non-`ACTIVE` users), added consistently and flagged in the M5c report.
- **Bulk-granting enrollment access is read → one `updateMany` → one email per row (M5c, emails added pre-deploy).** `bulkGrantAccess` first reads the selected rows that are still `AWAITING` (so it knows who to email), then runs a single `updateMany` over exactly those ids — still filtered on `accessState: "AWAITING"` inside the query, so a stale selection (a row already granted by someone else between page load and click) is silently skipped rather than erroring — then sends `sendAccessGrantedEmail` per row via `Promise.allSettled` after the write has committed. Sends are fail-safe: `mail.ts` never throws, and `allSettled` means one bad send can't stop the others or fail the action.
- **Emails: absolute links from `APP_URL`, or no send at all.** Only `src/lib/mail.ts` sends email and only it builds links. Missing/invalid `APP_URL` → `console.warn` + skip, never a relative link in a mail body and never a failed Server Action. Callers pass `submissionId`, not URLs.
- **There is no self-service password reset.** No reset-token model exists, so `/login` has no forgot-password link — it tells the user to contact their program admin, who uses `resetUserPassword` on `/admin/users/[userId]`. Emails are trimmed + lowercased at every entry point (signup, login/authorize, admin create, bootstrap).
- **Seed and verify tooling is localhost-only, with one documented exception (Phase A step 9).** `scripts/assert-local-db.ts` accepts a non-local host only when `ALLOW_SEED_HOST` names it exactly (bare hostname; pooled and direct Neon forms count as one host) — meant for a Neon *staging* branch seeded from a dev machine for a Vercel Preview. The production host, read as the `DATABASE_URL` host in `.env.neon`, is refused before the allow-list is consulted. `prisma/bootstrap*.ts` and `prisma/set-program-status.ts` don't use the guard at all; they are the Neon tools.
- **`updateEnrollmentStatus` only reaches `CANCELLED`/`DROPPED` (M5c).** `ACTIVE` is `grantAccess`'s job and `COMPLETED` is certificate issuance's job — the Zod schema deliberately excludes both so this more generic-sounding action can't become a backdoor around either one's own guard.
- **`assignMentorToBatch` verifies the target user's role is `MENTOR` (M5c).** Not enforced at the schema level — a `MentorAssignment` row can technically point at any `User` — so the action checks explicitly rather than letting an admin accidentally wire one to a LEARNER/ADMIN account (which every M5b mentor query would just silently filter out at `getMentorBatchIds`, inert but wrong).
- **Certificate issuance happens only on the `<100 → 100` transition, through the single `refreshEnrollmentProgress` call site (M5c, tightened pre-deploy).** `refreshEnrollmentProgress` reads the previously cached `Enrollment.progressPercent`, recomputes, and calls `issueCertificateIfEligible` only when the old value was `< 100` and the new one is exactly `100`. A learner already at 100 re-completing a lesson never re-enters issuance. `issueCertificateIfEligible` is called there and nowhere else — both `markLessonComplete` and `submitAttempt`'s quiz-completion path already funnel through that rollup (M4.5). The percent check is exact, never fuzzy: `getProgramProgress` rounds to `Math.round(x*1000)/10`, so full completion is always precisely `100`.
- **Certificate numbers are `LUM-{year}-{5-digit sequence}`, generated by finding the current max for that year and incrementing (M5c).** The only real race is two learners finishing in the same second computing the same next number — `issueCertificateIfEligible` retries the `create` once on a `P2002` conflict, recomputing the max before the retry.
- **Revocation sticks.** `issueCertificateIfEligible` refuses when a certificate of **any** status already exists for the `enrollmentId` — so after an admin `revokeCertificate`s one, no later rollup re-issues it (`scripts/verify-admin.ts` check 7 proves this with and without the `<100 → 100` transition). Re-issuing after a revocation would be a deliberate admin action; none is built.
- **A `QUIZ` lesson completes itself (M4.5).** When `Lesson.assessmentId` is set, `submitAttempt` marks that lesson's `LessonProgress.completed = true` iff `Assessment.passingScorePercent === null` (no threshold — any submission counts) OR the attempt's `passed === true`. A failed attempt (a threshold exists and wasn't met) does nothing — no upsert, and it does NOT un-mark a lesson completed by an earlier passing attempt (completion is monotonic; a later failed retake never revokes an earlier pass). The manual "Mark as Complete" button (`markLessonComplete`) is not rendered at all for `QUIZ` lessons. Both paths call `refreshEnrollmentProgress` (`src/lib/progress-rollup.ts`) — never recompute the rollup inline a third way.

- **A learner's curriculum is the program's PUBLISHED modules only (admin authoring).** `getProgramProgress` now filters `Module.status = PUBLISHED` (it used not to filter at all — harmless while every module came from the seed as PUBLISHED). A DRAFT module is invisible to learners and outside their percentage; `createModule` always creates DRAFT. This supersedes the older note under "Published assignment" that the tree is unfiltered.
- **An admin curriculum edit recalculates cached progress but never issues a certificate.** Publishing/unpublishing a module, or adding/deleting a lesson in a published module, calls `recalculateProgramProgress(programId)` (`progress-rollup.ts`), which rewrites `Enrollment.progressPercent` for every live enrollment and deliberately does **not** call `issueCertificateIfEligible`. An enrollment an edit leaves at exactly 100% with no certificate is listed on `/admin/certificates?tab=eligibility`, where `issueCertificate(enrollmentId)` issues it on purpose. That action is the **second** call site of `issueCertificateIfEligible` (the automatic one in `refreshEnrollmentProgress` is unchanged); it re-checks 100% and "no certificate of any status" first, so a revoked certificate is still never re-issued.
- **Content that learners have touched can't be deleted.** `deleteLesson` refuses when any `LessonProgress` row exists; `deleteModule` refuses when any lesson progress, attempt or submission hangs off it (unpublish instead); `deleteAssessment` refuses when it has attempts (archive instead). `publish` needs something real: a module needs ≥ 1 lesson, an assessment ≥ 1 question.
- **A question bank is frozen once any attempt exists.** `addQuestion` / `updateQuestion` / `deleteQuestion` / `duplicateQuestion` / `moveQuestion` all call `assertBankEditable` — `Answer` rows point at those questions and options, and a score was computed from them. Settings and status stay editable; `duplicateAssessment` makes an editable DRAFT copy in the same module (not linked to a lesson).
- **A QUIZ lesson can only link an assessment from its own module that no other lesson uses** (`resolveLessonAssessment`; `Lesson.assessmentId` is unique). Deleting an assessment clears the link rather than deleting the lesson.
- **Reordering swaps `order` values with the neighbour** (modules, lessons, questions) — orders may have gaps after deletes, so nothing assumes ±1. There is no drag-and-drop.
- **Batch rules.** A batch's program is fixed once created (`Enrollment`/`Certificate` carry their own `programId`). Capacity can't be set below the seats already held. Status moves only along `UPCOMING → ACTIVE → COMPLETED`, any → `ARCHIVED`, `ARCHIVED → UPCOMING`, `COMPLETED → ACTIVE`; it never touches `Enrollment` — access is not derived from batch status.
- **`createEnrollment` (admin) adds one gate the learner flow lacks: one live enrollment per program.** Plus the same open-batch, capacity and duplicate checks as `enrollAction`. With "grant access" it lands `GRANTED`/`ACTIVE` and the learner gets the email and the notification. `restoreAccess` is `SUSPENDED → GRANTED` (no email, status untouched).
- **`/admin/enrollments` no longer defaults to `accessState=AWAITING`** — the default is everything, with AWAITING rows sorted first (unchanged in `getEnrollmentsForAdmin`) and an "Awaiting (n)" access tab. The "Cancelled" status tab also matches `DROPPED`.
- **`AdminUserRow.lastActiveAt` is `User.lastActiveAt` as stored** (lesson completion only) — unlike the mentor screens, the admin users table does not derive it, so it is blank for mentors, admins and learners who only took quizzes.

## 4. Known gaps (schema does not model these — do not fabricate)

- **No admin authoring for assignments.** Programs, batches, modules, lessons, assessments and questions are all created and edited in `/admin`; assignments (with their rubric, instructions and resources) are still seed-only and shown read-only in the curriculum builder.
- **Lesson/assessment pages don't re-check `Module.status`.** A DRAFT module is hidden from the curriculum tree and from progress, but a learner who already has a lesson's or assessment's URL can still open it. Guarding those routes is the follow-up.
- **No admin Settings screens** (DECISIONS #13), no live sessions (batch "Sessions Completed", Schedule tab), no certificate template editor, no program image, no profile photos (initials avatars).
- **Announcements are in-app only**, there is no "sent" history (only the recipients' rows exist), and mentors have no inbox page.
- **No self-service password reset / no email verification** — no reset-token or verification model. Admin reset only (see Rules).
- **Skills / skill proficiency** — no `Skill` model. Any "skills acquired" UI needs a real field added first.
- **Real time tracking** — no session/duration log; see Learning Hours rule above.
- **Program categories** — `Program` has no category/tag field; catalog filter chips are not built.
- **"Saved" enrollment state** — My Learning's Stitch reference shows a Saved tab; no backing field exists (`EnrollmentStatus` has no SAVED value). Dropped, not faked.
